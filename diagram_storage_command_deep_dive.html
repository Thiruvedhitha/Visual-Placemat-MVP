Diagram internals Storage, identity, commands and rendering
Foundation to runtime
01 · Foundation

What is a catalog, and is it the diagram?

A catalog is the diagram's owning document record. The visible diagram is assembled from that catalog record, its capability rows, visual overrides and the current renderer.

A

Short answer: yes, at the product level

Users think of a catalog as one saved capability-map diagram. Technically, the catalog row is only the aggregate root: it owns metadata and points to many capability rows. ReactFlow is a rendering of that stored domain model, not the database model itself.

Document

capability_catalogs

One row per diagram. Stores name, owner/client, industry, status, per-node style JSON, chat history, legend and notes.

Content

capabilities

Many rows per catalog. Each row is one business capability node with its UUID, parent UUID, level and content.

Presentation

ReactFlow nodes

Generated in the browser from capabilities plus node_styles. Positions and visual containers are derived at render time.

Think of it as an aggregate

Catalog / diagram document ├── metadata: name, industry, owner, client ├── capabilities[]: semantic tree nodes ├── node_styles{nodeId}: fill, border, textColor and AI patches ├── chat_history: messages, commits and legend └── visual_maps[]: saved version snapshots The diagram displayed on screen = capabilities + styles + layout algorithm.
Important distinction A ReactFlow node is not stored as a ReactFlow JSON object. The application stores business capabilities, then buildCanvasNodes() creates ReactFlow nodes with coordinates, sizes and display data.
02 · Node anatomy

What exactly is one node?

One node has a durable semantic record, optional catalog-level visual overrides, and a temporary ReactFlow representation.

capabilities row

Durable node content and structure

{ id: "9c8...7a1", // node UUID catalog_id: "cat...01", // owning diagram parent_id: "2af...e04", // parent node UUID level: 2, name: "Account Management", description: "Manages accounts", note: "Review in Q4", sort_order: 3, source: "ai_generated", is_deleted: false }
node_styles JSON

Optional display overrides keyed by UUID

{ "9c8...7a1": { fill: "#dbeafe", border: "#2563eb", textColor: "#172033", note: "AI-added note patch", description: "AI patch" } }

03 · Tree model

How flat database rows become a tree

The database does not store nested JSON for the active diagram. It stores a self-referencing adjacency list.

Retail Bank id=A · parent_id=null · L0
Retail Banking id=B · parent_id=A · L1
Accounts · id=D · parent_id=B · L2
Lending · id=E · parent_id=B · L2
Digital Banking id=C · parent_id=A · L1
Mobile Channel · id=F · parent_id=C · L2
Web Channel · id=G · parent_id=C · L2

Parent lookup

parent = capabilities.find( cap => cap.id === node.parent_id )

Children lookup

children = capabilities.filter( cap => cap.parent_id === node.id )

ReactFlow rendering is visually nested

The dashboard currently passes edges={[]} to ReactFlow Parent-child relationships are expressed by calculated placement and nested visual containers, not visible connector edges. L0 is a band, L1 is a column, L2 is a contained section and L3 is a row inside it.
1

Index rows by UUID

buildCanvasNodes() creates a map of capability ID to a temporary TreeNode object.

2

Attach children

For every row, the builder pushes it into its parent's children[]. Rows with no parent become roots.

3

Assign display numbers

Sibling order creates numbers such as 1, 1.2 and 1.2.3. They are derived, not database IDs.

4

Calculate sizes and x/y

Levels, children and label lengths determine group width, column height and positions.

5

Merge node styles

The dashboard performs { ...node.data, ...nodeStyles[node.id] }, then ReactFlow renders CapabilityNode.

04 · Database

How one diagram is stored

The active diagram spans multiple tables. This is the concrete relationship model used by the current code.

capability_catalogs 1 ─────────── N capabilities id (PK) id (PK) name catalog_id (FK → catalog.id) node_styles JSONB parent_id (FK → capabilities.id) chat_history JSONB level, name, description, note │ └── self-reference builds tree capability_catalogs 1 ─────────── N visual_maps version_number is_active layout_data JSONB snapshot capability_catalogs 1 ─────────── N meeting_transcripts meeting_transcripts 1 ─────────── N transcript_proposals

capability_catalogs

Aggregate metadata. node_styles is a map keyed by capability UUID. chat_history holds conversation data, commits and legend.

capabilities

Current editable semantic state. The foreign key catalog_id groups nodes into a diagram; parent_id creates hierarchy.

visual_maps

An immutable-ish version snapshot created on every normal Apply. Stores capabilities and nodeStyles in layout_data.

transcript tables

Store source transcript, pipeline status and reviewable node/command/TODO proposal JSON before application.

Current save operation

1

POST /api/catalogs/save

Browser sends catalogId, catalogName, the full capability array and nodeStyles.

2

Create or update catalog

New diagrams insert a catalog. Existing diagrams update metadata, then delete all old capability rows.

3

Insert levels 0 → 3

Rows are inserted level-by-level so each parent's new DB UUID exists before its children are inserted.

4

Remap styles

tempToReal changes each node_styles key from the browser ID to the freshly generated database ID.

5

Create visual_maps version

Old versions become inactive; a new active snapshot stores remapped capabilities and styles.

Apply is a full replacement, not row-by-row synchronization For an existing catalog, the route deletes every capability row and reinserts the complete current tree. Consequently, database node UUIDs change on every normal Apply.
05 · UUID identity

How the system knows which node a command targets

Names are human-readable and can be duplicated. UUIDs are the command address.

ID

The LLM does not independently discover the node

The server serializes the current diagram into the system prompt with each node's name, level, hierarchy number and exact UUID. The LLM copies the required UUID into nodeId, parentId or newParentId.

System prompt excerpt produced by renderTree() 1 Retail Bank [id: 11111111-1111-4111-8111-111111111111] 1.1 Retail Banking [id: 22222222-2222-4222-8222-222222222222] 1.1.1 Account Management [id: 33333333-3333-4333-8333-333333333333] User "Rename Account Management to Customer Account Management" LLM response { "commands": [{ "type": "RENAME_NODE", "nodeId": "33333333-3333-4333-8333-333333333333", "newName": "Customer Account Management" }] }

Execution uses exact ID matching

Valid address

idx = capabilities.findIndex( cap => cap.id === cmd.nodeId ) Found → update that row only

Invalid address

idx === -1 errors.push( `node "${cmd.nodeId}" not found` ) No mutation occurs

06 · Command runtime

From LLM JSON to an edited canvas

Commands are plain JSON mutation instructions. The LLM proposes them; deterministic application code validates and executes them.

1

AIMapEditor builds request

Sends user prompt, current capabilities, nodeStyles, legend, mode and up to 20 history turns to POST /api/transform.

Browser → Next.js API
2

Server builds system prompt

Command definitions, rules, legend and a textual diagram tree containing exact IDs are assembled.

promptBuilder.ts
3

OpenAI returns JSON

Command mode expects { commands: DiagramCommand[], summary }. Suggest mode wraps one command in each proposal.

gpt-4.1-mini · response_format=json_object
4

Dashboard separates legend commands

SET_LEGEND and REMOVE_LEGEND update the Zustand legend. Other commands go to executeCommands().

5

Executor validates and mutates copies

Structural commands change the capability array. Style/note patches change the nodePatches map. Errors are returned and shown as toasts.

6

pushUndoAndSet updates local state

Previous state enters the undo stack; React state and Zustand receive the result; isDirty=true.

7

ReactFlow rebuilds

The changed capability array is transformed into nodes again and style patches are merged into node data.

8

User clicks Apply

Only then does /api/catalogs/save replace the database capabilities and create a version snapshot.

07 · Existing diagram

How LLM commands edit an existing diagram

This path uses the UUIDs already loaded from the database into the browser.

1

Load catalog by ID

GET /api/catalogs/:catalogId returns catalog metadata, node_styles, chat_history and ordered capability rows.

2

Hydrate Zustand and dashboard state

The UUIDs returned by Supabase become the IDs used by ReactFlow nodes and the style map.

3

Send live state to transform API

AIMapEditor reads useCatalogStore.getState().capabilities at request time, avoiding an old prop snapshot.

4

LLM sees names plus UUIDs

For command mode the server may trim deep nodes by relevance; selected nodes are force-included. Chat/suggest mode sends all nodes.

5

Executor finds exact UUID

If it exists and validation passes, the command changes local state. Otherwise the canvas remains unchanged for that command.

6

Apply persists complete state

The full post-command capability array and style map are sent to the save API.

Example: move L2 "Payments" under L1 "Digital Banking" { "type": "REPARENT_NODE", "nodeId": "payments-uuid", "newParentId": "digital-banking-uuid" } Executor checks: 1. payments-uuid exists 2. digital-banking-uuid exists 3. Digital Banking level === Payments level - 1 4. drag/drop hierarchy logic accepts the move 5. parent_id and sort_order are updated locally
08 · Template transcript

How commands survive template cloning

The transcript LLM analyzes the original template, but the user must receive a new independent catalog. The application bridges those two UUID spaces.

1

Pipeline loads template rows

template_id identifies a catalog. Its capabilities are fetched with original template UUIDs.

2

Pass 2 receives template YAML

Every node includes its original UUID, name and level. The LLM returns command proposals using those UUIDs.

3

User reviews proposals

Commands remain stored in transcript_proposals.payload, still addressed to original template IDs.

4

Apply creates a new catalog

applyNewFromTemplate() inserts a separate capability_catalogs row for the user.

5

Clone creates fresh node UUIDs

Each original template node receives a new UUID. Parent IDs are remapped during copy.

6

Remap every command address

nodeId, parentId, newParentId and insertAfterId are changed from old template IDs to cloned IDs.

7

Execute against cloned capabilities

The same deterministic executeCommands() now sees matching IDs in the cloned tree.

8

Persist result and transcript highlights

Structural changes, node_styles, amber borders, legend and proposal statuses are written to the new catalog.

09 · Save and restore

Current state versus version snapshots

The capabilities table represents current state. visual_maps preserves Apply-time snapshots for history and restore.

Current

capabilities + node_styles

Read when opening the dashboard. This is the mutable current diagram used by normal editing and AI prompts.

History

visual_maps.layout_data

Every normal Apply inserts a version containing a capability snapshot and nodeStyles, with one version marked active.

User selects a version

2

Undo/redo stacks are cleared and the restored capabilities/styles become the visible diagram.

10 · Analysis notes

Observed implementation caveats

These points are based on the current implementation and matter when reasoning about IDs and persistence.

1. Browser IDs are not refreshed after normal Apply The save route creates fresh database node UUIDs and remaps stored parents/styles, but returns only catalog/version IDs. The dashboard calls markSaved() without replacing its in-memory capabilities with the newly inserted rows. Reopening the catalog reloads correct IDs; continuing immediately after Apply may use stale browser IDs.
2. Every Apply regenerates IDs Existing capability rows are deleted and reinserted. Stable UUID identity across versions would normally require upsert/update/delete-by-diff rather than full replacement.
3. Legend persistence follows a separate path The dashboard's normal save body contains capabilities and nodeStyles, not legend. Legend lives in Zustand and is also placed in chat_history.legend by transcript and chat-history flows. This should be treated as a distinct persistence concern.
4. AI notes can live in node_styles SET_NOTE writes a patch rather than capabilities.note. Manual notes and transcript TODOs use the capability column. A single canonical storage location would simplify load/save and reporting.
5. Transcript edit persistence differs from normal Apply applyEdit() updates/inserts/soft-deletes targeted capability rows directly, preserving existing UUIDs. Normal dashboard Apply performs full delete/reinsert and version creation. These are two different persistence strategies.
